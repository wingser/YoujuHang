# 实战案例复盘

这些是本项目真实踩过的坑。**方法论的价值大于结论本身**——重点看每个案例是
「怎么定位的」，而不只是「结论是什么」。

---

## 案例 1：516/517 走错路径（2026-08-28）

**现象**：进区持续失败 `ret=-14 UNHANDLED_MSG_ID zone 0x204 516 / 0x205 517`

**定位**：翻 `hang_spectate_20260827.pcapng`，看真实客户端的 HTTP/2 请求路径。
发现 516/517 的 `:path` 是 `/game/`，而 1024~1092 才是 `/zone/2/`。

**结论**：进区握手走 `/game/`，区/房间消息走 `/zone/2/`。此前一律发到 `/zone/2/`。

**教训**：**先看 `:path` 再猜协议**。同一个 gate 连接、同一套 base64 封帧，
路径不同就是不同的处理器。抓包第一步应是列出所有 `:path` 的分布。

## 案例 2：房间消息全部 `-10 WRONG_GAME_TOKEN`（2026-08-29）

**现象**：进区成功（517 返回 ret=1、5989 字节），但随后所有建房/进房都返回
`ret=-10`，日志里 `bodyLen=29`。两个账号、6 个不同房间号全部一样。

**错误假设链**（走了很多弯路）：

1. 以为是房间号问题 → 但 JOIN 同一个号在探针里能成功
2. 以为是消息序列问题（516→517 顺序）→ 实测不是
3. 以为是"响应加密无法解析" → 实测 1025 是明文

**定位方法：对照实验**。写一个探针程序，对同一账号、同一房间号，
只改一个变量看服务器返回：

```
变体A：登录 → 516 → 517 → 1026 JOIN 43   → ret=-10 WRONG_GAME_TOKEN
变体B：登录 → 512 → 516 → 517 → 1026 JOIN 43  → ret=1 成功
```

**结论**：程序从不发送 `EnterLobbyCMsg(512)`。512 是 token 的激活步骤。

**为什么难发现**：`/game/` 侧消息（516/517/任务/战队/签到）**不发送 512 也能正常响应**，
只有 `/zone/2/` 的房间消息校验 token 激活状态。517 成功造成了「token 没问题」的错觉。

**教训**：

- **A/B 对照实验是最有力的定位手段**。控制变量，一次只改一处。
- 当「A 成功、B 失败」时，不要只比较 B 的参数，**要比较 A 和 B 的完整前置序列**。
- 响应长度能反推错误内容：`29 = 11 + 2 + 16("WRONG_GAME_TOKEN")`。
  日志只有 `bodyLen` 时也能定位。

## 案例 3：1025 房间列表"强加密"是误判（2026-08-29）

**现象**：代码注释与文档都写着「1024/1025 响应为 58105 强加密数据，
Go 端无解密能力，故只能随机选号盲试」。于是程序随机猜房间号 1~150，
建房失败就加入同一个号——两条路都走不通，长期无法建房。

**定位**：探针程序直接发 1025，请求体只带 `f1=uid f2=token`（不带任何额外参数），
返回 **24390 字节明文 protobuf**，解析出 **187 个房间**。

**结论**：

- 1025 完全可以解析。此前的"加密"判断是错的（可能当时请求带了额外参数，
  或看到的是 18140 加密通道的流量）。
- 房间号必须取自列表：列表外（如 188）建房 → `-19 ROOM_NOT_FOUND`；
  列表内已被占用 → `-87 WRONG_ROOM_STATUS`。
- 用 `RoomInfo.f7` 判断空闲：为 0 即无人，可直接建房。

**教训**：

- **文档里"无法解析/是加密的"这类否定性结论，要亲手验证一次再采信**。
  这类结论一旦被写进注释，会误导后续所有判断，代价极高。
- 请求体参数不同，响应形态可能完全不同。试试最简请求。

## 案例 4：建房成功的判定字段用错（2026-08-29）

**现象**：建房明明返回 `ret=1`，程序却判定失败。

**定位**：对比两种成功响应的完整结构：

```
建房成功：  f1=1, f4={f1=roomId, f2=cfg, f7=本机uid, ...}     ← 无顶层 f3，无 f5
进他人房间：f1=1, f3=255, f4={..., f5={f1=本机uid,f2=255}, f7=房主uid}
```

**结论**：旧代码用「本机是否出现在 playerList(f5)」判断建房成功，
**但建房成功的响应里根本没有 f5**。必须用 `f4.f7 == uid`（IsHost）判定。
（另外旧代码把 playerList 误读成 f4，实际是 f5。）

**教训**：**成功路径和失败路径的响应结构可能不同**，不能想当然。
把每种真实响应完整 dump 出来逐字段对比，不要只比对 ret。

## 案例 5：把正常返回码当失败，导致建房后立刻被踢（2026-08-29）

**现象**：修复进房后，建房成功但很快重建房间。

**定位**：探针跑完整流程，发现 `1092` 在房主与观战身份下**恒定**返回
`-142 SNAPSHOT_NO_SRAM`，而代码里 `stFail >= 3` 就判定断线 → 5 秒内必然触发。

同样的问题还有两个：

- `1033` 上位失败返回 `-35 SLOT_OCCUPIED`，但 HTTP 仍是 200，只看 error 会误判成功，
  进而开始发 1028 被 `-29 NOT_PLAYING` 连续拒绝 → 再次误判断线。
- 断线重建时**没有先离房**，房间号仍被自己占着，下一轮建房/进房都被拒，死循环。

**结论**：区分「传输层失败」与「业务返回码」。只有前者和致命返回码才累计失败。

**教训**：

- **HTTP 200 ≠ 业务成功**。私有协议必须校验业务返回码。
- **先枚举一遍"正常情况会返回哪些非 1 的码"，再把它们显式列为非失败**。
  否则默认「非 1 即失败」的写法一定会误伤。
- 状态机进入异常分支时，检查是否需要先做清理动作（如离房）再重试。

## 案例 6：`parseZoneResp` 多跳 2 字节（2026-08-27）

**现象**：响应解析错位，ret 丢失，误判失败。

**定位**：`/zone/2/` 响应在 2026-08-26 后改为纯 protobuf（无 MsgID 前缀、非 zlib），
而旧代码 `resp[2:]` 仍按老格式跳过前缀，把 `08 01`（f1=ret）跳掉了。

**教训**：**协议会变**。老代码里的偏移/前缀假设要在每次大规模失败时重新验证一遍。

## 案例 7：密码与 base64 编码坑（2026-08-26）

- 密码 = `MD5(明文).upper()`（32 hex 大写，无盐、无双重哈希）
- body 必须 **base64url**（`-` `_`），标准 base64（`+` `/`）会被拒：
  随机 raknetId 的 varint 常产生 `+`/`/`，导致 `illegal base64 data at input byte N`

**教训**：编码细节导致的失败往往报在最外层，看起来像网络问题。先确认编码再查别的。

## 贯穿所有案例的方法论

1. **先宏观后微观**：先列出抓包里所有的 `:path` / 端口 / msgid 分布，建立全景，
   再钻进具体某条消息。
2. **相信实测，质疑文档**：特别是"这东西是加密的/不可解析/做不到"这类断言。
3. **对照实验**：写一个能直接对服务器发请求的探针，控制变量逐个验证假设。
   这是本项目定位问题最有效的手段，比反复读代码有效得多。
4. **完整 dump 再下结论**：不要只看 ret，把成功/失败/边界三种响应都完整展开对比。
5. **把结论写回代码注释并注明抓包证据**（pcap 文件名 + 日期 + 实测数值），
   让下一个接手的人不必重跑一遍。
6. **区分"传输失败"与"业务返回码"**，并显式枚举正常但非 1 的返回码。
