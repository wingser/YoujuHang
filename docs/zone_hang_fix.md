# 战盟任务整夜未完成的诊断与修复

## 现象
Go 挂机程序整夜运行，但战盟任务（2000-2008，尤其 2002/2003/2004 在线时长类）无任何进度。
日志持续出现：`enter zone failed ret=0 err=UNHANDLED_MSG_ID zone 0x205 517`

## 抓包逆向结论（hang_spectate_20260827 / join_room_20260827）
`/zone/2/` 路径（18141 端口）**一直是明文协议** `base64url([2B MsgID LE][protobuf])`，
**并不存在"zone 协议加密"**（加密的是 18140 大厅连接，挂机程序不依赖它）。
真实客户端进区 / 建房 / 心跳的消息序列（msgid + 固定前缀 `08 f4 a5 ef 02 12 20` + 32hex 会话 token）：

| 步骤 | 真实 msgid | 含义 |
|------|-----------|------|
| 进区前置 | **516** (QueryZoneInfo) | 先查区信息，建立会话 |
| 进区 | **517** (EnterZone) | 正式进入分区 |
| 查房 | 1024 / 1025 | 房间列表 |
| 进房/送礼 | 1080 / 1026 | 进房或建房（f1,f2,f3=roomId,f8=1）|
| 心跳 | 1028 | 每秒 1 次 |
| **在线时长上报** | **1042** | **房主身份每秒 1 次，f3={f1=3, f2=递增tick}** |
| 状态轮询 | 1092 | 约 1.6s |
| 快照(观战) | 1032 | 观战身份保活 |
| 上位/离房 | 1033 / 1027 | |

关键：房主（建房/上位成功）身份在挂机循环中**每秒发一次 1042**，其 `f3.f2` 为递增计数器
（真实客户端每秒 +52~60）。该消息驱动服务器累计房主在线时长（战队任务 2002/2003/2004）。

## 根因
1. **进区只发 517，缺 516 前置查询**：`EnterZone` 直接发送 `EnterZoneCMsg=517`，但服务器在
   2026-08-26 后的协议要求**先 516 建立会话再 517 进入**。孤立的 517 被拒
   → `UNHANDLED_MSG_ID zone 0x205 517` → 整夜进不了区 → 后续全未执行。
2. **`parseZoneResp` 错误跳过 2 字节**：`/zone/2/` 响应为纯 protobuf（无 MsgID 前缀，非 zlib），
   旧代码 `resp[2:]` 跳过 `08 01`（field1=ret），导致解析错位、ret 丢失、误判失败。
3. **缺失 1042 在线时长上报**：挂机循环未发送 1042，即使进区成功，房主在线时长也不被累计，
   战队任务时长类（2002/2003/2004）不推进。
4. **BuildEnterZone / BuildZoneInfo 缺 f3=3**：真实请求均含 `f3=3` 固定字段，缺失可能被服务端判定异常。

## 修复（server/internal）
- `room/room.go` `EnterZone`：先 `QueryZoneInfoCMsg(516)` 再 `EnterZoneCMsg(517)`。
- `room/room.go` `parseZoneResp`：去除 `resp[2:]` 跳过，直接返回 protobuf 体。
- `room/room.go` 玩家身份循环：心跳后同步发送 `OnlineReport(1042)`，tick 从 1124000 起每帧 +56。
- `protocol/msgid.go`：新增 `RoomOnlineReportCMsg=1042` 与 `BuildOnlineReport`（f3={f1=3,f2=tick}）。
- `protocol/msgid.go` `BuildEnterZone/BuildZoneInfo`：补充 `FieldVarint(f,3,3)`。

## 备注
- 建房请求真实结构为 f1,f2,f3=roomId,f8=1（无 f4/f5）。当前 `BuildCreateRoom` 仍保留 f4=1+f5=cfg，
  因手动挂机历史可成功，暂不改动以免引入回归；若建房失败可优先排查此处。
- 1042 的 `f2` 初值/增量系按真实抓包量级近似（服务器仅校验递增与频率），如需精确可进一步逆向房主
  进房响应下发的基准值（1026 响应 f3=9280 暂未确认即为其基准）。

## 进房策略（查列表选号，建房优先、失败就近观战）

> **2026-08-29 更正**：本节原「技术约束」称 1025/1024 响应是 58105 强加密、Go 端无法解密，
> 因而只能随机盲猜房间号。**该结论是错的**——实测 1025 请求体只带 `f1=uid f2=token` 时，
> 响应就是明文 protobuf，可直接解析出全部房间（实测 187 条，房间号 1..187）。
> 这个错误判断导致长期无法建房，是本项目代价最高的一次误判。以下为更正后的实现。

- **房间号全部取自 `QueryZoneRoomListCMsg(1025)`**（`room.QueryRooms` / `RoomBrief`）：
  `RoomInfo.f7`（房主 uid）为 0 即空闲号，可直接建房；非 0 表示已有人，可进房观战。
- **候选选择**（`pickRooms`）：随机打散后各取 3 个空闲号与 3 个已占用号
  （常量 `hangCreateTries`），避免多账号挤同一间。
- **决策流程**（`enterRoom`）：
  1. 依次在空闲号上 `CreateRoom`（isCreate + cfg）；
  2. **建房成功判定 = `RoomInfo.f7 == uid`（IsHost）**，不是 IsPlayer——
     实测建房成功的响应里根本没有 f5 玩家列表，用 IsPlayer 会永远判不出来；
  3. 空闲号全部失败 → 依次 `JoinRoom` 已占用房间，成功则观战；
     - 观战进入后先停留 `HangSpectateBefore` 模拟正常玩家，再 `ChangeRoomSlot(1033)` 尝试上位；
     - **必须校验 1033 的返回码**：房间已有玩家时返回 `-35 SLOT_OCCUPIED` 但 HTTP 仍是 200，
       只看 error 会误判上位成功，随后发 1028 被 `-29 NOT_PLAYING` 连续拒绝。
       上位失败则保持观战挂机（观战时长同样计入战盟任务）；
  4. 全部候选被拒 → 等待 `HangPickRetry`（30 秒）后重新查列表再试。
     （原实现失败后等 1 小时，白白浪费一整轮。）
- **多账号**：每个账号在自己的 goroutine 里各查一次列表、各选自己的候选，
  状态不共享；撞号时以服务器房间列表为天然互斥表（A 建成后 B 再查会看到 Host=A）。

### 遗留问题（2026-08-29 仍未确认）

自建房当房主时房间里只有自己一人，战盟任务「在任意游戏内玩或观战」**是否计入**
尚未验证（1042 在线上报返回 ret=1，机制上应该计入，但需跑满 1 小时确认）。
若实测不计入，把 `enterRoom` 里「先建房」与「先进他人房间」两个循环对调即可改为观战优先。
